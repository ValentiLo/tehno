# Трассировка требований

**Трассировка требований** — это установление и документирование **связей** между требованиями и другими артефактами проекта: проектными решениями, кодом, тестами, документацией.

Простыми словами: это **карта**, которая показывает, **откуда пришло требование**, **где оно реализовано** и **чем проверяется**.

---

## Зачем нужна трассировка

| Цель | Что даёт |
|---|---|
| **Полнота** | Убедиться, что все требования реализованы |
| **Контроль изменений** | Понять, что затронет изменение требования |
| **Тестирование** | Проверить, что каждое требование покрыто тестом |
| **Отчётность** | Показать заказчику, что всё выполнено |
| **Анализ влияния** | Оценить последствия изменений |
| **Соответствие** | Доказать соответствие стандартам (ГОСТ, ISO) |

---

## Виды трассировки

### 1. Прямая трассировка (Forward)

От **требования** к **реализации**.

```
Требование → Проект → Код → Тест
```

**Вопрос:** «Где реализовано это требование?»

### 2. Обратная трассировка (Backward)

От **кода/теста** к **требованию**.

```
Код → Проект → Требование
```

**Вопрос:** «Зачем нужен этот код? Какое требование он реализует?»

### 3. Трассировка между требованиями

Связи **между самими требованиями**:
- **Зависимость** — одно требование зависит от другого.
- **Конфликт** — требования противоречат друг другу.
- **Дублирование** — одно и то же требование описано дважды.
- **Детализация** — одно требование уточняет другое.

---

## Матрица трассировки

Основной инструмент — **таблица**, где строки — требования, столбцы — артефакты.

**Пример:**

| Требование | Проект | Код | Тест | Статус |
|---|---|---|---|---|
| **ФТ-1** Регистрация | Модуль «Авторизация» | `auth.c` | T-01 | ✅ Выполнено |
| **ФТ-2** Вход в систему | Модуль «Авторизация» | `auth.c` | T-02 | ✅ Выполнено |
| **ФТ-3** Восстановление пароля | Модуль «Авторизация» | `auth.c` | T-03 | ⏳ В работе |
| **НФТ-1** Время отклика ≤ 2 с | Архитектура | — | T-10 | ⏳ В работе |

## Пример трассировки в реальном проекте

**Требование ФТ-1:** «Система должна позволять пользователю зарегистрироваться по email».

| Этап | Артефакт | Связь |
|---|---|---|
| **Бизнес-требование** | БТ-1: увеличить базу клиентов | Породило ФТ-1 |
| **Требование** | ФТ-1: регистрация по email | — |
| **Проектное решение** | Модуль `UserManager` | Реализует ФТ-1 |
| **Код** | `user_manager.py`, метод `register()` | Реализует ФТ-1 |
| **Тест** | `test_register.py::test_email_registration` | Проверяет ФТ-1 |
| **Документация** | Руководство пользователя, раздел 3.1 | Описывает ФТ-1 |

**Итог:** ФТ-1 **трассируется** от бизнес-требования до теста. Если ФТ-1 изменится — мы **знаем**, что нужно править `user_manager.py`, тест и документацию.

## Инструменты трассировки

| Инструмент | Что делает |
|---|---|
| **Jira** | Связи между задачами, требованиями, тестами |
| **Confluence** | Документирование требований и связей |
| **Azure DevOps** | Трассировка требований → код → тесты |
| **ReqView** | Специализированный инструмент для трассировки |
| **DOORS** | IBM Rational DOORS — для крупных проектов |
| **Excel / Google Sheets** | Простая матрица трассировки |

**Пример в Jira:**
- Задача `PROJ-101` (требование)
- Связана с `PROJ-102` (проектирование)
- Связана с `PROJ-103` (реализация)
- Связана с `PROJ-104` (тест)

## Трассировка в ГОСТ

**ГОСТ 34.601-90** требует **трассировку** на этапах:
- Разработка ТЗ → трассировка к требованиям пользователя.
- Проектирование → трассировка к ТЗ.
- Реализация → трассировка к проекту.
- Тестирование → трассировка к требованиям.

**ГОСТ 19.201-78** — ТЗ должно содержать **связи** между требованиями и этапами.

## Зачем это нужно на практике

### Пример 1: Изменение требования

**Заказчик:** «Добавьте возможность регистрации через Google».

**Что нужно изменить (благодаря трассировке):**
- ФТ-1 — обновить.
- `user_manager.py` — добавить метод.
- Тесты — добавить `test_google_registration`.
- Документацию — обновить.

**Без трассировки:** можно забыть про тесты или документацию.

### Пример 2: Проверка полноты

**Вопрос:** «Все ли требования реализованы?»

**Благодаря матрице:**
- Открываем список требований.
- Смотрим столбец «Код».
- Если пусто — требование **не реализовано**.

### Пример 3: Проверка тестов

**Вопрос:** «Все ли требования покрыты тестами?»

**Благодаря матрице:**
- Открываем столбец «Тест».
- Если пусто — требование **не покрыто**.

## Типичные ошибки

| Ошибка | Последствие |
|---|---|
| Нет трассировки | Забытые требования, непокрытые тесты |
| Трассировка только «в одну сторону» | Не видно, зачем нужен код |
| Устаревшая матрица | Неточная картина |
| Слишком детальная | Трудоёмко поддерживать |
| Слишком общая | Бесполезна |

| **Обратная** | Код → Требование |
| **Матрица** | Таблица связей |

## Итог

**Трассировка требований** — это **карта связей**:
- **Откуда** пришло требование (бизнес-цель, заказчик).
- **Где** оно реализовано (проект, код).
- **Чем** проверяется (тест).

**Помогает:**
- Не забыть требования.
- Контролировать изменения.
- Покрывать тестами.
- Отчитываться перед заказчиком.

**Инструменты:** Jira, Confluence, Azure DevOps, Excel.

**Стандарты:** ГОСТ 34.601-90, ГОСТ 19.201-78.
