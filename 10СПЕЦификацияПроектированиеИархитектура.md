##  Что такое требования

**Требование** — это описание того, что система должна делать, какими свойствами обладать и в каких условиях работать.

**Требования отвечают на вопросы:**
- **Что** должна делать система?
- **Как** она должна это делать?
- **Для кого** она предназначена?
- **В каких условиях** она будет работать?

**Почему требования важны:**
- **Основа проекта** — всё дальнейшее проектирование, разработка и тестирование опираются на требования.
- **Снижение рисков** — чёткие требования уменьшают вероятность переделок.
- **Контроль** — по требованиям проверяют готовность продукта.
- **Коммуникация** — требования — это «язык» между заказчиком и разработчиком.

**Последствия плохих требований:**
- Проект выходит за сроки и бюджет.
- Продукт не соответствует ожиданиям заказчика.
- Много переделок на поздних этапах.
- Конфликты между командой и заказчиком.

## Страница 3. Классификация требований

### 3.1. Функциональные требования

**Что система должна делать.**

**Примеры:**
- Система должна позволять пользователю зарегистрироваться.
- Система должна формировать отчёт по продажам за месяц.
- Система должна отправлять уведомления на email.

### 3.2. Нефункциональные требования

**Как система должна работать.**

| Категория | Пример |
|---|---|
| **Производительность** | Время отклика — не более 2 секунд |
| **Надёжность** | Доступность — 99,5% в год |
| **Безопасность** | Шифрование данных по TLS 1.3 |
| **Удобство** | Обучение нового пользователя — до 2 часов |
| **Масштабируемость** | До 10 000 одновременных пользователей |
| **Совместимость** | Работа в Chrome, Firefox, Safari |

### 3.3. Бизнес-требования

**Зачем нужна система с точки зрения бизнеса.**

**Примеры:**
- Сократить время обработки заявки на 30%.
- Увеличить прибыль на 15%.
- Снизить операционные расходы.

### 3.4. Требования пользователей

**Что нужно конкретному пользователю.**

**Примеры:**
- Риелтор должен быстро находить объекты по фильтрам.
- Бухгалтер должен выгружать отчёты в Excel.

### 3.5. Системные требования

**Технические условия работы.**

**Примеры:**
- ОС: Windows Server 2022, Linux Ubuntu 22.04.
- СУБД: PostgreSQL 15.
- Минимальный объём ОЗУ: 8 ГБ.

## Страница 4. Спецификация требований (SRS)

**SRS (Software Requirements Specification)** — документ, описывающий полный набор требований к ПО.

**Зачем нужен SRS:**
- Единый источник истины для команды.
- Основа для проектирования и тестирования.
- Юридический документ (при спорах с заказчиком).

**Структура SRS по IEEE 830:**

1. **Введение**
   - Назначение
   - Область применения
   - Определения, сокращения
   - Ссылки

2. **Общее описание**
   - Перспектива продукта
   - Функции продукта
   - Характеристики пользователей
   - Ограничения
   - Предположения и зависимости

3. **Конкретные требования**
   - Функциональные требования
   - Внешние интерфейсы
   - Нефункциональные требования

4. **Приложения**
   - Глоссарий
   - Модели данных

## Страница 5. Методы сбора требований

### 5.1. Интервью

**Что:** беседа с заказчиком и пользователями.

**Плюсы:** глубокое понимание, уточнение деталей.

**Минусы:** трудоёмко, зависит от квалификации интервьюера.

### 5.2. Анкетирование

**Что:** письменный опрос.

**Плюсы:** охват большого числа пользователей.

**Минусы:** нет возможности уточнить ответы.

### 5.3. Наблюдение

**Что:** наблюдение за работой пользователей.

**Плюсы:** выявление неочевидных требований.

**Минусы:** требует времени, пользователи могут вести себя иначе.

### 5.4. Анализ документов

**Что:** изучение существующей документации, регламентов, инструкций.

**Плюсы:** быстро, не требует контакта с людьми.

**Минусы:** документация может быть устаревшей.

### 5.5. Прототипирование

**Что:** создание макета системы.

**Плюсы:** наглядность, обратная связь от заказчика.

**Минусы:** затраты на создание, риск «застрять» на прототипе.

### 5.6. Мозговой штурм

**Что:** коллективная генерация идей.

**Плюсы:** много идей за короткое время.

**Минусы:** требует модератора, не все идеи реализуемы.

## Страница 6. Анализ и приоритизация требований

### 6.1. Проверка требований

**Критерии качественного требования:**

| Критерий | Что означает |
|---|---|
| **Полнота** | Все аспекты учтены |
| **Непротиворечивость** | Нет конфликтов между требованиями |
| **Однозначность** | Понимается одинаково всеми |
| **Проверяемость** | Можно проверить выполнение |
| **Реализуемость** | Технически возможно |
| **Необходимость** | Действительно нужно |

### 6.2. Приоритизация

**Методы:**
- **MoSCoW:** Must have, Should have, Could have, Won't have.
- **Метод парных сравнений:** попарное сравнение требований.
- **Ранжирование по стоимости и важности.**

### 6.3. Трассировка требований

**Что:** связь требований с другими артефактами.

**Зачем:**
- Проверить, что все требования реализованы.
- Отследить изменения.
- Оценить влияние изменений.

**Матрица трассировки:**

| Требование | Проект | Код | Тест |
|---|---|---|---|
| ФТ-1 | Модуль А | a.c | T-1 |
| ФТ-2 | Модуль Б | b.c | T-2 |

## Страница 7. Что такое проектирование ПО

**Проектирование ПО** — процесс создания проекта программного обеспечения, а также дисциплина, изучающая методы этого процесса.

**Цели проектирования:**
- Преобразовать требования в **архитектуру** и **детальный проект**.
- Обеспечить **сопровождаемость** и **расширяемость**.
- Разделить систему на **модули** и **компоненты**.
- Определить **интерфейсы** между частями.

**Уровни проектирования:**

| Уровень | Что проектируется |
|---|---|
| **Архитектурное** | Система в целом, подсистемы |
| **Модульное** | Модули, классы, функции |
| **Детальное** | Алгоритмы, структуры данных |

**Этапы:**
1. Анализ требований.
2. Архитектурное проектирование.
3. Детальное проектирование.
4. Реализация.
5. Тестирование.

## Страница 8. Принципы проектирования

### 8.1. Абстракция

Скрытие деталей реализации. Пользователь видит **что**, а не **как**.

**Пример:** класс `Список` — методы `add()`, `remove()`, но не важно, как хранятся данные.

### 8.2. Инкапсуляция

Данные и методы объединены в одном месте, доступ — через интерфейс.

### 8.3. Модульность

Система разбита на независимые модули.

### 8.4. Слабая связанность (Loose Coupling)

Модули мало зависят друг от друга.

### 8.5. Высокая связность (High Cohesion)

Модуль делает **одну задачу хорошо**.

### 8.6. Принципы SOLID

| Принцип | Расшифровка |
|---|---|
| **S** | Single Responsibility — одна ответственность |
| **O** | Open/Closed — открыт для расширения, закрыт для изменения |
| **L** | Liskov Substitution — подстановка Барбары Лисков |
| **I** | Interface Segregation — разделение интерфейсов |
| **D** | Dependency Inversion — инверсия зависимостей |

### 8.7. Принципы GRASP

- **Information Expert** — ответственность у того, у кого данные.
- **Creator** — кто создаёт объекты.
- **Controller** — кто обрабатывает запросы.
- **Low Coupling, High Cohesion.**
- **Polymorphism** — через интерфейсы.

## Страница 9. Архитектура ПО: основные понятия

**Архитектура ПО** — набор основных проектных решений о системе.

**Что включает архитектура:**
- **Компоненты** — крупные части системы.
- **Связи** между компонентами.
- **Интерфейсы** — как компоненты взаимодействуют.
- **Ограничения** — что нельзя делать.
- **Технологии** — что используется.

**Зачем нужна архитектура:**
- **Основа для реализации** — разработчики знают, что делать.
- **Коммуникация** — общий язык для команды.
- **Снижение рисков** — проблемы видны на раннем этапе.
- **Сопровождаемость** — легче вносить изменения.

**Кто отвечает:**
- **Архитектор ПО** — главный ответственный.
- **Тимлид**, **ведущие разработчики** — участвуют.

**Документирование архитектуры:**
- **UML-диаграммы** — прецедентов, классов, последовательностей, состояний.
- **ГОСТ 19** (ЕСПД) — программные документы.
- **ГОСТ 34** — автоматизированные системы.
- **Схемы**, **описания**, **спецификации**.

## Страница 10. Архитектурные стили и паттерны

### 10.1. Монолит

**Что:** вся система — один блок.

**Плюсы:** простота разработки, единая кодовая база.

**Минусы:** сложно масштабировать, изменения затрагивают всё.

### 10.2. Клиент-сервер

**Что:** клиент запрашивает, сервер обрабатывает.

**Плюсы:** централизованные данные, разделение ответственности.

**Минусы:** сервер — единая точка отказа.

### 10.3. Трёхуровневая архитектура

**Что:** представление → логика → данные.

**Плюсы:** разделение, масштабируемость.

### 10.4. Микросервисы

**Что:** система из маленьких независимых сервисов.

**Плюсы:** независимое развёртывание, масштабируемость.

**Минусы:** сложность, распределённые транзакции.

### 10.5. SOA (сервисно-ориентированная архитектура)

**Что:** сервисы взаимодействуют через шину (ESB).

**Плюсы:** переиспользование, интеграция.

### 10.6. Событийно-ориентированная

**Что:** компоненты реагируют на события.

**Плюсы:** слабая связанность, асинхронность.

### 10.7. Паттерны проектирования (GoF)

| Паттерн | Назначение |
|---|---|
| **Singleton** | Единственный экземпляр |
| **Factory Method** | Создание объектов |
| **Observer** | Подписка на события |
| **Strategy** | Взаимозаменяемые алгоритмы |
| **Adapter** | Совместимость интерфейсов |
| **Decorator** | Добавление функциональности |
| **Facade** | Упрощённый интерфейс |

## Итоги лекции

- **Требования** — основа проекта: функциональные, нефункциональные, бизнес-, пользовательские, системные.
- **SRS** — документ с полным описанием требований по IEEE 830.
- **Методы сбора:** интервью, анкеты, наблюдение, анализ документов, прототипы, мозговой штурм.
- **Проектирование** — переход от требований к архитектуре и деталям.
- **Принципы:** абстракция, инкапсуляция, модульность, SOLID, GRASP.
- **Архитектура** — компоненты, связи, интерфейсы, ограничения.
- **Стили:** монолит, клиент-сервер, микросервисы, SOA, событийные.
- **Паттерны:** Singleton, Factory, Observer, Strategy и др.
